## Part 8 — `ExpansionService`: the create-or-reuse decision

User gave a very detailed 5-step spec for the service (verbatim, paraphrased here): (1) guard against double-expansion by reading `expansion_status` — expanded returns existing children with no LLM call, expanding returns what's there, otherwise mark expanding and continue; (2) gather prompt context — sibling labels + parent chain up to root; (3) call the expander — one LLM call, nothing persisted yet; (4) resolve each proposal — normalize, look up `(track_id, normalized_label)`, hit writes an edge only, miss creates the topic + edge + enqueues enrichment, using attempt-insert-and-catch-constraint rather than check-then-insert to avoid a race; (5) return — mark parent expanded, send back children with resources for reuse hits. Also specified the transaction shape explicitly: step 2 short read txn, step 3 no txn at all, steps 4-5 short write txn, and explicitly flagged **"annotating the whole method `@Transactional` is the mistake."** Named the two supporting collaborators: `TopicExpander` (LLM call) and `LabelNormalizer` (normalizes the LLM's output).

- **Decisions (user, via AskUserQuestion, before design):**
  1. **Enrichment enqueue in the miss branch:** no-op with a `// TODO` — no queue exists yet, confirmed out of scope for this pass.
  2. **Package location for `TopicExpander`/`LabelNormalizer`/records:** inside `node/service/` (not a new `node/llm/` top-level folder) — chosen over the alternative that was later adopted anyway once the package got crowded (see Part 10).
  3. **Controller wiring:** wire `NodeController.expandTopic` up now to call `ExpansionService` and return real JSON — chosen over leaving it service-layer-only.
- Plan agent produced the detailed design. Key resolved design questions (Claude's engineering calls, presented in the plan and not objected to):
  - **Transaction mechanism:** two `TransactionTemplate` fields (`requiredTemplate` = `PROPAGATION_REQUIRED`, `requiresNewTemplate` = `PROPAGATION_REQUIRES_NEW`) built from an injected `PlatformTransactionManager` in the constructor — resolves the fact that `@Transactional` is proxy-based and breaks on self-invocation, which a single orchestrating method needing several distinct boundaries would hit.
  - **Constraint-violation handling refined beyond the user's literal wording:** catching a `DataIntegrityViolationException` must happen *outside* the `TransactionTemplate.execute(...)` lambda, not inside it — Postgres aborts the whole transaction/connection on the first violation, so any further statement on that connection (even a "harmless" re-read) would also fail. Per proposal, this means topic resolve-or-create and edge insertion are **two separate `REQUIRES_NEW` transactions**, not one — specifically so a losing edge-insert race can never roll back an already-committed topic creation.
  - **Error handling added beyond the user's literal wording:** if the LLM call or resolution throws after a topic was marked `expanding`, nothing would ever unstick it (the guard treats `expanding` as "in flight" forever) — so steps 2-5 are wrapped in `try/catch`, marking the topic `failed` on any exception, and the guard's claimable set was extended to `{not_expanded, failed}` so a failed topic is retryable.
  - **The atomic claim itself** uses a `@Modifying @Query` bulk `UPDATE ... WHERE expansion_status IN (:claimableStatuses)` rather than read-then-write, since entities are `@Getter`-only with no setters (consistent with the whole session's entity design) and a bulk conditional update is also the correct way to make the claim itself race-free.
- Implemented: `TopicRepository.claimForExpansion`/`updateExpansionStatus`; `TopicExpander` (`@AiService`, `@SystemMessage`/`@UserMessage` prompt, `@V`-annotated parameters — pre-formatted `String`s rather than raw `List<String>` to avoid relying on uncertain Mustache list-iteration syntax); `LabelNormalizer` (**initially built as a second `@AiService`** — this was wrong, corrected in Part 9); `ProposedChild` record; `ExpansionService` itself (guard → gather context → LLM call → resolve/persist per proposal → mark expanded/failed → return); response DTOs `ExpandTopicResponse`/`ExpandedChild`/`ResourceView`; `NodeController.expandTopic` rewired.

## Part 12 — `EnrichmentService`: filling a topic with resources and concepts

- **A real design tension in the user's own spec, worked through via a plan, then via actual testing:** the spec asked for two things that don't normally fit together — one transaction atomic across all roots, *and* the same insert-first-catch-the-violation-and-reread handling `ExpansionService` uses per topic. `ExpansionService`'s pattern uses `PROPAGATION_REQUIRES_NEW` per item specifically so one item's constraint violation can't take down its siblings — the opposite of "atomic across all roots" — and catching a `DataIntegrityViolationException` inside one ordinary transaction doesn't work either, since Postgres aborts the whole transaction on the first error.

'true'` — addressed by adding a custom `transactionManager` bean (`config/TransactionManagerConfig.java`) with `setNestedTransactionAllowed(true)`. Second symptom, which persisted even after that fix: `NestedTransactionNotSupportedException: JpaDialect does not support savepoints`.
